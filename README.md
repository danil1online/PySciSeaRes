# vak-adverts-list

Ежедневный синхронизатор и поисковая система по авторефератам диссертаций ВАК (vak.gisnauka.ru).

## Задача

Система предназначена для автоматического сбора, хранения и поиска информации о диссертациях, защищающихся по специальностям ВАК. Основной функционал:

- **Ежедневная синхронизация** — автоматический обход объявлений о защите по всем специальностям за последние 30 дней
- **Скачивание авторефератов** — сохранение PDF-файлов авторефератов диссертаций
- **Автоматическое извлечение данных** — извлечение публикаций и данных научного руководителя из PDF
- **Поиск и фильтрация** — поиск по специальностям (компактный интерфейс с поиском), датам защиты, ключевым словам
- **Вопросы к базе данных** —natural language queries к БД через LLM
- **Экспорт в Excel** — выгрузка результатов поиска в табличном формате
- **API-документация** — встроенная страница `/docs` с описанием всех эндпоинтов

## Методология

### Логика обработки объявлений

При ежедневном запуске скрипт определяет, является ли защита новой или существующей, по совпадению **ФИО + дата защиты**:

**Новая защита** (нет в БД по ФИО + дата):
1. Скачивает автореферат
2. Извлекает публикации (JSON-LLM → Regex → merge с дедупликацией)
3. Записывает `pub_extract_attempts = 1`
4. Ищет email-адреса для всех публикаций
5. Записывает `email_search_attempts = 1`

**Существующая защита** (уже есть в БД):
- **≥5 публикаций**: проверяет `email_search_attempts`
  - ≥2 — пропускает
  - 1 + есть email — пропускает
  - 1 + нет email или 0 — запускает поиск email
- **<5 публикаций**: проверяет `pub_extract_attempts`
  - ≥2 — пропускает
  - <2 — извлекает публикации заново

Скрипт хранит resolved URL PDF-файла в БД (`autoref_pdf_url`). При повторном запуске, если URL изменился, старый PDF удаляется и скачивается новый.

### Многоуровневое скачивание PDF

Ссылка на автореферат в базе ВАК может вести не на PDF-файл напрямую, а на HTML-страницу. Скрипт использует многоуровневый алгоритм:

**Этап 1: Прямой PDF**
- Если URL заканчивается на `.pdf` — скачивается напрямую
- URL кодируется (пробелы → `%20`) для корректной работы с сервером

**Этап 2: Проверка Content-Type**
- URL содержит индикаторы PDF (`avtoreferat`, `get-file`, `download`, `file/`, `send/`, `attachment`)
- Делается HEAD-запрос для проверки `Content-Type: application/pdf`
- Если PDF — скачивается напрямую

**Этап 3: Поиск PDF на HTML-странице**
- Анализ HTML через BeautifulSoup с 5 стратегиями (по приоритету):
  1. **Текст ссылки = «автореферат»** — `<a>автореферат</a>` → `.pdf`
  2. **Контекстный поиск** — слово «автореферат» рядом со ссылкой в HTML (родитель/соседние элементы)
  3. **Действие + PDF** — слова «Посмотреть файл» / «Скачать» + контекст «автореферат»
  4. **Скоринг** — сортировка кандидатов по баллам (автореферат +100, диссертация/протокол/отзыв -200)
  5. **LLM-анализ** — при неоднозначности (разрыв скоров < 30) отправляется страница в LLM для выбора правильного кандидата

**Этап 4: Скачивание**
- Файлы < 200 КБ отбрасываются (автореферат обычно 300 КБ — 1 МБ+)
- URL кодируется перед скачиванием

**Примеры:**
- `https://vak.ru/.../id` → прямая ссылка на `file.pdf` — скачивается сразу
- `https://vak.ru/.../avtoreferat.html` → HEAD проверяет Content-Type → скачивается PDF
- `https://vak.ru/.../cgoev` → страница с `<a href="...pdf">Автореферат</a>` — стратегия 1
- `https://vak.ru/.../larionov` → `Автореферат диссертации: <a href="...pdf">Посмотреть файл</a>` — стратегия 2
- `https://vak.ru/.../barinov` → много PDF (протоколы, отзывы, диссертация) — скоринг + LLM

### Retry-логика для VAK API

Все HTTP-запросы к VAK API используют экспоненциальную задержку при ошибках:
- **ConnectionError/Timeout** — повтор через 1, 2, 4 секунды (макс. 3 попытки)
- **HTTP 429/502/503/504** — повтор через 1, 2, 4 секунды (макс. 3 попытки)
- **Другие HTTP-ошибки** — немедленный выход

### Контроль памяти

Скрипт отслеживает потребление RAM через `psutil` и управляет памятью:
- **Мягкий лимит (12 ГБ)** — при превышении выполняется принудительный сбор мусора `gc.collect()`
- **Критический лимит (14 ГБ)** — аварийная остановка скрипта с `sys.exit(1)`
- **Пакетная обработка** — каждые 10 объявлений проверяется память
- **PDF читается один раз** — текст сохраняется в переменную и передаётся в оба экстрактора, вместо открытия PDF-файла дважды
- **Освобождение после обработки** — текст PDF удаляется `del pdf_full_text` после извлечения всех данных

### Требования к ресурсам (эмпирические расчёты)

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| **ОЗУ минимум** | 8 ГБ | Система + скрипт + 143 PDF + SQLite |
| **ОЗУ рекомендуется** | 16 ГБ | Запас для LLM-запросов и GC |
| **Диск** | 500 МБ | PDF (182 МБ) + БД (~50 МБ) + окружение |
| **Время обработки** | 30-60 мин | ~30 объявлений/чел, LLM 25 сек/запрос |
| **LLM-запросов на объявление** | 2 | Публикации + руководитель |

Расчёт памяти на одно объявление:
- PDF-текст: 50-100 стр × ~2 КБ = **100-200 КБ** (один раз в памяти)
- LLM-запросы (2 × 3500 символов): **~10 КБ** в момент запроса
- SQLite буфер: **~50 КБ** на транзакцию

При 200 объявлениях: 200 × 150 КБ (текст PDF) = **30 МБ** текста в процессе обработки. GC срабатывает каждые 10 объявлений.

### Извлечение публикаций

Используется гибридный подход с поэтапной обработкой и выводом результатов каждого этапа:

**Этап 1: JSON-LLM (приоритетный)**
- Отправка последних ~5 страниц автореферата (12 000 символов) в LLM (Qwen3.5-4B) с промптом для извлечения в формате JSON
- Структура результата: `authors` (массив), `title`, `journal`, `conference`, `year`, `volume`, `issue`, `pages`, `extra`
- Если JSON получен валидный (даже пустой []) — результат используется
- **Кэширование**: результаты сохраняются в `llm_responses/cache/` (TTL 7 дней)
- Лог: `JSON-LLM: N публикаций (Xс)`

**Этап 2: Regex (fallback)**
- Regex-парсинг от начала найденного раздела публикаций
- Лог: `Regex: N публикаций (раздел: ...)`

**Этап 3: LLM (fallback)**
- LLM-экстракция (те же последние ~5 страниц)
- Лог: `LLM: N публикаций`

**Этап 4: Объединение**
- Если regex ≥ 3, берётся как основа, LLM дополняет. Если LLM больше — берётся LLM
- Дедупликация через нормализацию текста (удаление дефисов, пунктуации, регистр)
- Максимум 30 публикаций на диссертацию
- Если после извлечения < 5 публикаций — при следующем запуске скрипт перескачает и пересчитает

### Извлечение руководителя

LLM-запрос к первым трём страницам автореферата с системным промптом для извлечения ФИО и места работы научного руководителя в формате JSON. **Кэширование**: результаты сохраняются в `llm_responses/cache/`.

### Валидация публикаций

Система эвристик для отсевания ложных срабатываний:
- Паттерны не-публикаций: "основные положения", "диссертация состоит", "в первой главе" и др.
- Предлоги в начале строки: "на основе", "в ходе", "по результатам" и др.
- Глагольные начала: "анализ", "разработ", "провед" — отсеиваются без сильных/слабых индикаторов публикации (DOI, "//", "журн", "вак", "scopus", годы, тома, страницы)

### Вопросы к базе данных (LLM QA)

Пользователь задаёт вопрос на русском языке, LLM генерирует SQL-запрос, выполняется к БД, результат форматируется и возвращается как ответ.

**Безопасность:**
- Разрешены только SELECT-запросы (DROP, DELETE, UPDATE, ALTER и др. заблокированы)
- Автоматическое добавление LIMIT 100
- Валидация перед выполнением

**Процесс:**
1. Пользователь задаёт вопрос (например: "У кого из соискателей больше всего публикаций?")
2. Система получает контекст БД (количество записей, примеры данных, список специальностей)
3. LLM генерирует SQL-запрос на основе системного промпта с описанием структуры БД
4. SQL выполняется, результаты форматируются (таблица, список, текстовый ответ)
5. Ответ показывается пользователю вместе с выполненным SQL-запросом

**Примеры вопросов:**
- "Сколько всего диссертаций в базе?"
- "У кого из соискателей больше всего публикаций?"
- "Какие соискатели защищаются по специальности 2.2.11?"
- "Какие научные руководители встречаются чаще всего?"
- "Какие направления публикаций по научной специальности 2.2.11 актуальны?"

## Внешние системы

### vak.gisnauka.ru API
- Базовый URL: `https://vak.gisnauka.ru/api`
- Эндпоинты:
  - `GET /att/adverts/` — поиск объявлений о защите (параметры: specialty, date_defend_from/to, page, page_size)
  - `GET /att/adverts/{id}/` — детали объявления
- Rate limiting: задержка между запросами не реализована (риск блокировки при частых запусках)
- Retry-логика: экспоненциальная задержка при ConnectionError/Timeout/5xx

### LLM-сервер
- URL: `http://195.133.13.56:1234/v1/chat/completions` (настраивается в config.py)
- Модель: `qwen3.5-4b`
- API совместим с OpenAI Chat Completions
- Таймаут: 120 сек, max_tokens: 2000, temperature: 0.1
- JSON-LLM таймаут: 300 сек (для cold start)
- **Кэширование**: ответы сохраняются в `llm_responses/cache/` (TTL 7 дней)

## Порядок запуска

### 1. Установка зависимостей

```bash
cd vak-adverts-list
python3 -m venv env
source env/bin/activate
pip install -r requirements.txt
```

### 2. Подготовка данных

Создать файл `sci_spec.txt` со списком специальностей ВАК в формате:

```
1.2.1 - Искусственный интеллект
1.2.2 - Системы обработки изображений
...
```

Формат: `шифр - название специальности` (каждая специальность с новой строки).

### 3. Запуск веб-приложения

```bash
python app.py
```

Сервер запустится на `http://0.0.0.0:5000`. Для продакшена использовать gunicorn:

```bash
gunicorn -w 4 -b 0.0.0.0:5000 app:app
```

### 4. Первоначальная настройка

1. Перейти на `http://localhost:5000/login`
2. Создать первого пользователя (администратора):

```bash
python3 -c "
import bcrypt
from flask import Flask
from app import app
from auth import create_user
with app.app_context():
    create_user('admin', 'your-password', True)
"
```

3. Войти в систему, перейти в `/admin` для создания дополнительных пользователей.
4. Перейти на `/docs` для просмотра API-документации.

### 5. Ежедневная синхронизация

Запуск вручную:
```bash
python daily_sync.py
```

Автоматический запуск по cron (каждый день в 3:00):
```cron
0 3 * * * cd /path/to/vak-adverts-list && source env/bin/activate && python daily_sync.py >> logs/sync.log 2>&1
```

### 6. Тестирование

Запуск всех тестов:
```bash
python3 -m pytest tests/ -v
```

Запуск конкретных модулей:
```bash
python3 -m pytest tests/test_pdf_search.py -v
python3 -m pytest tests/test_publications.py -v
python3 -m pytest tests/test_integration.py -v
```

Запуск с отчётом о покрытии (требует `pytest-cov`):
```bash
pip install pytest-cov
python3 -m pytest tests/ -v --cov=. --cov-report=html
```

Охват тестами:
- **config** — 15 тестов (конфигурация, пути, API-параметры)
- **daily_sync** — 13 тестов (sanitization, specialties, memory control)
- **download** — 10 тестов (скачивание PDF, кэширование, Content-Type, ошибки)

Проект содержит 112 тестов, охватывающих все ключевые модули. Тесты проверяют:
- Корректность конфигурации и путей
- Функции sanitization имён файлов

Запуск:

### Тестирование LLM (qwen3.5-4b)

Модель протестирована на примерах вопросов к базе данных:

| Вопрос | Результат |
|--------|-----------|
| "Сколько всего диссертаций в базе?" | ✅ 187 записей |
| "У кого из соискателей больше всего публикаций?" | ✅ Маматказин И.Р. (25 pubs) |
| "Автор по специальности 2.2.11 с макс. публикаций" | ✅ Валитов Р.Р. (14 pubs) |
| "Уникальных специальностей в базе" | ✅ 55 |
| "Соискатели по специальности 2.3.1" | ✅ 15 результатов |
| "Направления публикаций по 2.2.11" | ⚠️ Вернул счёт, а не названия |
| "Руководитель с макс. диссертациями" | ⚠️ Неверный GROUP BY |

**Выводы:**
- Простые запросы (COUNT, LIST, GROUP BY) работают хорошо
- Сложные аналитические запросы могут генерировать неоптимальный SQL (ограничение 2B модели)
- Для продакшена рекомендуется Qwen3.6-35B

### Кэширование LLM-ответов
Результаты LLM-запросов сохраняются в `llm_responses/cache/` с TTL 7 дней. Это ускоряет повторные запуски синхронизации и снижает нагрузку на LLM-сервер.

### Валидация SQL-запросов
QA-модуль валидирует SQL-запросы перед выполнением:
- Разрешены только SELECT-запросы
- Автоматическое добавление LIMIT 100
- Блокировка опасных операций (DROP, DELETE, UPDATE, ALTER и др.)

### API-документация
Встроенная страница `/docs` с описанием всех эндпоинтов, параметров и форматов ответов.

## Примечания

- Авторефераты с размером менее 200 КБ считаются неполными и не обрабатываются
- Обнаружение новой/существующей защиты происходит по **ФИО + дата защиты**
- Счётчики `pub_extract_attempts` и `email_search_attempts` ограничивают повторные попытки до 2 на каждую защиту
- При недоступности LLM-сервера используется только regex-извлечение
- При недоступности LLM-сервера извлечение руководителя завершается с `null`
- PDF-файл читается один раз за объявление, текст передаётся в оба экстрактора (публикации + руководитель)
- Данные в БД обновляются через `INSERT OR REPLACE` по `id` — повторные запуски не создают дубликатов
- Публикации перезаписываются для каждого объявления при обработке (DELETE + INSERT)
- Скрипт синхронизации автоматически контролирует память и делает GC каждые 10 объявлений
- Ссылка на автореферат может вести на HTML-страницу — скрипт ищет PDF-ссылки с текстом «автореферат» через BeautifulSoup
- Пароли хранятся в виде bcrypt-хешей
- База данных использует WAL-режим для лучшей конкурентной производительности
- LLM-кэш можно отключить установкой `VAK_CACHE_ENABLED=0`
- Пути к БД нормализованы через `os.path.normpath()` для корректной работы из любых модулей
